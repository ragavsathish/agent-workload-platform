# Expand the one big wall, phase by phase

**Scope:** the complete [Big Picture wall](one-big-wall.md), from ordinary owner work through alert investigation, AWP change, PR soundtrack, deployment, and component regeneration in any selected repository. This is a desk-derived decision overlay, not a completed workshop or a proposal to put every note into one event store.

| EventStorming phase | Overlay on the same wall | Status |
| --- | --- | --- |
| **1 · Decision mechanics** | Read model → command handler → deriver → repository → resulting event or refusal, for every major branch | **This document** |
| **2 · Aggregates and bounded contexts** | Group decisions by consistency boundary; draw language and authority boundaries | [Phase 2 overlay](phase-2-aggregates-contexts.md) |
| **3 · Policies** | Add “whenever…” reactions, refusal and failure rules, and version checks to the agreed boundaries | [Phase 3 overlay](phase-3-policies.md) |

In this phase, **read model** means information a decision needs, whether projected, queried, or assembled on demand. A **command handler** authenticates and orchestrates reads, a decision, a commit, and external effects. A **deriver** is the pure or deterministic decision over command facts and loaded state; an LLM answer or code generator is an effect, not a trusted deriver. **Repository** means the state-owning port or external system used by the handler; it does not automatically mean a Git repository. `Current` means a path exists in code or documented manual workflow. `Proposed` means the cross-path decision contract is still design work. No new storage is implied by a proposed repository port.

```text
command + read model → deriver → decision
command handler: authenticate → load → derive → commit or refuse → invoke effect → report outcome
repository: provides the state/version for the decision and persists its accepted outcome
```

## Handoffs between decision points

- **D2 → D3:** admission records a task identity; execution may later fail without retroactively turning admission into refusal. Owner unavailability after submission yields an **unconfirmed** outcome until the same stable request ID is reconciled.
- **D1 → D4 and D5:** journal/classification and daily account are independent durable tasks. A completed turn does not serialize their completion order.
- **D7 → D8:** a selected firing alert can start investigation automatically. Its finding is evidence for an owner or future governed change decision; it does not authorize production edits by itself.
- **D9 → D10–D11:** a qualified AWP diff can enter the PR workflow. The current manual soundtrack path and proposed qualification gate have different maturity.
- **D14 → D10 or D15:** one selected candidate enters the AWP PR path when AWP is the target; another repository keeps its own PR and release authority.
- **D15 → D12:** a reviewed finding may change a **new** spec cut. The old cut and its candidate evidence remain attributable.

## Phase 1 questions left on the wall

1. **Admission equivalence:** The owner chose one task for retries. Which input fields define the same intent? The owner currently compares the entire serialized payload, including retry-varying trace context.
2. **Knowledge review:** What evidence shows the owner's approval was recorded before a personal claim is projected as accepted? The current review paths should be narrated with a knowledge reviewer.
3. **PR soundtrack:** Does missing audio hold an AWP self-evolution PR, or can a named reviewer record an exception? The manual guide makes soundtrack optional for other changes.
4. **Regeneration authority:** Who ratifies the spec cut and selects one candidate for each target repository? The target repository's reviewer and release operator retain promotion authority.

Phase 2 groups these decisions into aggregates and bounded contexts, using the minimum consistency questions needed to justify each boundary. [Phase 3](phase-3-policies.md) attaches “whenever…” policies, refusals, and failure reactions to those boundaries and tests duplicate delivery, stale reads, concurrent selection, and failed effects.
