# Phase 3 — policies on the one big wall

This overlays **green policy notes** on the [event-first wall](one-big-wall.md), using [Phase 1 decision points](expanded-storming.md) and [Phase 2 aggregate/context boundaries](phase-2-aggregates-contexts.md). A policy says **“Whenever this event occurs, if this information says the rule applies, an authorized actor issues this command.”** The outcome is a new event, a known refusal, a held state, or an unconfirmed effect. Policies can be manual. These notes do not imply a production event bus, automatic handler, or shared transaction across contexts.

`Current` means code or a documented manual step supports the rule today. `Proposed` means the rule is a candidate to validate before implementation. `Open` means the wall exposes a choice without selecting a rule. The aggregate IDs A1–A13 and context IDs C1–C9 are defined in Phase 2.

## Ordinary work and evidence

| Policy | Whenever / read model | Authorized command and owner | Outcome or exception | Status / boundary |
| --- | --- | --- | --- | --- |
| **P1 · Delegate once** | Whenever a Task Request is submitted, load owner identity, canonical instruction/workspace, stable request ID, and A2's prior mapping. | C2 Tasking derives admit, identical replay, or conflict; the handler commits one native task for an admitted request. | `Task accepted`; identical retry returns that task; invalid or conflicting request is refused. If the owner response is uncertain, reconcile using the **same** ID. | Owner chose stable retries; Gateway support proposed. A2 → A3. |
| **P2 · Run accepted work** | Whenever `Task accepted` is recorded, load A3's task input, execution mode, selected workspace, capability grant, and image state. | C2 starts bounded execution through C8; the task handler prepares workspace, captures public progress and result. | `Task result captured` or `Task failure retained`. Preparation failure is a task failure after acceptance. | Current. A3 ↔ C8. |
| **P3 · Present a task artifact** | Whenever a task reports completion, load its native result and artifact reference under the authenticated identity. | C2 serves only the artifact named for that task/workspace. | Artifact returned; missing or mismatched artifact yields explicit lookup failure without rewriting completion. | Current. A3 and artifact store. |
| **P4 · Extract attributed knowledge** | Whenever an owner Turn completes and source identity is available, inspect source turn/message IDs. | C1 submits separate journal and classification work through C2 for C3. | Attributed suggestions become reviewable independently; one failed extraction does not invalidate the answer or the other task. | Current. A1 → A2/A3 → A4. |
| **P5 · Review knowledge** | Whenever a knowledge suggestion is presented, load its source and current review interpretation. | Owner accepts, corrects, rejects, or leaves it pending through C3's review command. | A Review Event changes the current interpretation; an unreviewed suggestion does not become an accepted Profile Fact by inference. | Current owner action; A4 projection atomicity open. |
| **P6 · Build the daily account** | Whenever a daily build is requested, load owner, date/time zone, bounded source set, and prior matching request. | C2 submits one idempotent daily task; C3 writes the account from the chosen source set. | `Daily account written` or task failure. A changed source set needs an explicit new request/version. | Current task identity; A5 version semantics open. |
| **P7 · Render a reviewed song** | Whenever a complete lyric manifest is available, load the entire manifest, cancellation state, and whether render was already requested. | Owner reviews and approves the manifest, then C2 starts one render task for A6. | `Song stored`, render failure, or a known not-ready/cancelled/already-rendering refusal. | **P8 · Investigate a firing alert** | Whenever a managed alert is firing, load the allowlisted rule, incident fingerprint/epoch, prior submission, cooldown, and bounded Prometheus facts. | C4 derives incident identity and submits one bounded C2 investigation with a stable request ID. | Investigation finding or retained task failure; duplicate polling does not create another task in the same epoch. | Current. A7 → A2/A3. |
| **P9 · Review before changing product** | Whenever an answer, task result, knowledge item, song, or alert finding is ready for owner review, load source evidence and provenance. | Owner closes, follows up, or nominates a specific change. | `Work closed`, `Follow-up requested`, `AWP change nominated`, or `Component nominated`. An alert alone does not authorize code changes. | Current human review; governed automatic nomination remains proposed. C1–C4 → C6/C7. |

## Component regeneration and learning

| Policy | Whenever / read model | Authorized command and owner | Outcome or exception | Status / boundary |
| --- | --- | --- | --- | --- |
| **P15 · Ratify a replaceable cut** | Whenever a component is nominated, load target repository/base, interface, write authority, sourced behavior, and independent gate obligations. | Component owner accepts the boundary and ratifies an immutable A9 spec cut. | `Component boundary accepted` and `Spec cut ratified`, or a held boundary/cut with a reason. | **P16 · Prove the fence** | Whenever a spec cut is ratified, load its digest, permitted inputs, old implementation location, and private judge boundary. | C7 operator verifies the clean-room fence before any generator starts. | `Clean room verified` or `Regeneration held before generation`. | **P18 · Judge every candidate** | Whenever a candidate artifact exists, load its cut/boundary identity and complete independent gate evidence. | C5 measures the candidate outside generator control and records pass, fail, or unjudged. | **P19 · Select exactly one** | Whenever the eligible set is complete enough for review, re-read it, the target base revision, and the current A11 selection version. | Authorized reviewer selects one digest; handler uses a version guard and checks the base again. | `One candidate selected`, or refusal for no eligible candidate, stale base, or competing selection. | **P20 · Enter target release process** | Whenever one candidate is selected, load target repository, selected digest, spec cut, gate report, and rollback evidence. | Target maintainer opens that repository's PR. | **P21 · Learn into a later cut** | Whenever a held candidate, failed release, or operational finding is reviewed, load its source and the ratified cut it tested. | Component owner decides whether to amend behavior, evaluation, or implementation freedom, then proposes a **new** spec version. | `Spec learning recorded`, or a finding remains open. Prior cut and candidate measurements stay attributable. | Proposed. C7/A9. |

## Failure and concurrency checks for the policy walkthrough

- **Duplicate delivery:** P1 and P8 reuse stable IDs; P17–P18 retain per-candidate identity. Replaying a notification must not duplicate work or overwrite evidence.
- **Unknown commit:** A transport timeout after P1 or P8 is not a known refusal. Reconcile the existing ID before issuing new work.
- **Stale read:** P11, P14, P19, and P20 recheck the pinned revision or decision version when acting, rather than relying on an earlier read model.
- **Concurrent candidates:** P18 can converge to an eligible set; P19 still requires one versioned selection. The [simulation](parallel-source-simulation.md) tests a related synthetic cross-owner projection, not this live candidate race.
- **External effect failure:** Missing artifact, song render failure, PR rejection, deployment failure, and unproved fence each have a visible end or owner action. A task result or passing measurement cannot stand in for a later effect.

**Open rule decisions:** canonical task intent for retries; atomic knowledge review projection; durable lyric approval; AWP soundtrack exception; AWP change nomination authority; candidate-selection key across competing runs. Resolve these with the responsible owner before turning proposed policy cards into automated handlers.
