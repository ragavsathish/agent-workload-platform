# Reducing retained Gondolin task VM disk use

Research date: 2026-10-20. Scope: `@earendil-works/gondolin` **0.13.0** and the Pi task VM integration in this repository. This note records checkpoint-size measurements and optimization options. The historical Patrol checkpoints described below have since been explicitly disposed; their logs and results remain. Current storage-driver measurements are in the [benchmark report](../../platform/agent-execution/gondolin-session/benchmarks/README.md), and the in-guest Docker choice is documented in the [Overlay2/VFS research note](gondolin-docker-storage-driver-overlay2-vs-vfs.md).

## Current footprint and representation

An earlier three-VM Patrol run used 64 GiB *virtual* disks; the saved checkpoints allocated **1,842, 946, and 1,841 MiB** on the host, and the workspaces allocated **698, 576, and 699 MiB**. VM 2's Patrol command was interrupted during setup, so its smaller disk was not a like-for-like comparison. These historical results are retained in the curated [benchmark-results.json](../../platform/agent-execution/gondolin-session/benchmarks_py/benchmark-results.json); use allocated bytes or host free-space change, not virtual size, for savings claims. The checkpoint files have since been disposed.

A read-only guest audit found the dominant checkpoint growth in Playwright browsers. The fresh VM had `/ms-playwright` at **658,300 KiB** (`ffmpeg-1011` 3,324 KiB and `chromium-1237` 654,964 KiB). Retained Patrol VM 1 had `/ms-playwright` at **2,524,256 KiB**, including additional `chromium-1194` (595,780 KiB), `headless_shell-1194` (323,200 KiB), `chromium-1208` (616,356 KiB), and `headless_shell-1208` (330,612 KiB). The directory grew by **1,865,956 KiB (~1,822 MiB)**, close to the **1,842 MiB** checkpoint allocation. The workspace package lock specifies Playwright **1.58.2**, and the Patrol run log records `npx playwright install chromium` fetching browser revision **1208**. At the time, the fresh and retained VMs were inspected through disposable overlays, leaving their source checkpoints intact. Those historical checkpoints have since been disposed. Sources: [workspace package lock](../../products/voice-agent/apps/client/package-lock.json), [consolidated benchmark results](../../platform/agent-execution/gondolin-session/benchmarks_py/benchmark-results.json), [benchmark report and raw evidence paths](../../platform/agent-execution/gondolin-session/benchmarks/README.md). The audit measurements are local observations; the curated result records establish the benchmark and checkpoint measurements.

Gondolin checkpoints are qcow2 overlays backed by an immutable guest rootfs, with a **Gondolin JSON metadata trailer appended to the same file**. Resume reads that trailer and starts a fresh qcow2 overlay backed by the checkpoint. When the resumed VM is checkpointed, Gondolin safely rebases the new overlay directly onto the guest rootfs, collapsing the intermediate checkpoint ancestry. The integration stages a new checkpoint and renames it over the prior one only after checkpointing succeeds. Sources: [Gondolin checkpoint](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/checkpoint.ts), [Gondolin VM checkpoint](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/vm/core.ts), [local session integration](../../platform/agent-execution/gondolin-session/session.ts).

## Practical options, in order

1. **Align Playwright browser versions before saving future Patrol VMs.** The local guest audit points to multiple full Chromium revisions in `/ms-playwright`, rather than Docker, pub, or npm caches, as the main source of retained checkpoint growth. Build the browser revision actually required by the workspace's locked Playwright version into the common immutable guest image, or provide an immutable shared browser cache outside each writable guest overlay, then validate Patrol. Browser binaries in a common base image or shared mount do not need to be copied into each VM's qcow2 overlay. Do not delete older revisions from existing snapshots without checking which Playwright installation still uses them. A host-mounted workspace is separate from the qcow2 checkpoint and needs its own audit. Sources: [Gondolin qcow2 backing-file behavior](https://www.qemu.org/docs/master/tools/qemu-img.html), [Pi VM mounts](../../platform/agent-execution/gondolin-session/pi-extension.ts), [workspace package lock](../../products/voice-agent/apps/client/package-lock.json).
2. **Compact checkpoints offline with `qemu-img convert`.** QEMU documents that conversion of growable images suppresses empty/zero sectors; `-c` adds qcow2 compression, with `compression_type=zstd` or `zlib`. Compressed clusters remain readable but are rewritten uncompressed on later guest writes, so the saving is best suited to a stopped, retained checkpoint. This must be an explicit transaction on an inactive VM: convert to a separate staged qcow2 with the *same rootfs backing file and explicit backing format*, append the Gondolin trailer again, verify guest-visible equality with ordinary `qemu-img compare`, run `qemu-img check` and `VmCheckpoint.load`/resume, then atomically replace the original. **Plain `qemu-img convert` output is not a resumable Gondolin checkpoint** because it omits the custom trailer. A local conversion of a temporary copy of Patrol VM 1, using qcow2 compression and the same raw backing rootfs, reduced allocated bytes from **1,841.6 to 641.0 MiB (65.2%)** in **28.39 s**. After restoring the trailer, `qemu-img check` exited 0; ordinary `qemu-img compare` reported **“Images are identical”** in 4.54 s; and `GondolinSession` resumed the compressed copy and ran a guest `/bin/sh` check successfully (exit 0). This establishes technical viability for a stopped checkpoint; the effect on later writes and repeated resume/checkpoint cycles still needs measurement. Measure destination allocated bytes and resume latency before choosing compressed versus uncompressed conversion. Sources: [QEMU image utility](https://www.qemu.org/docs/master/tools/qemu-img.html), [Gondolin trailer parser/writer](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/checkpoint.ts), [Gondolin rootfs backing handling](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/vm/core.ts).
3. **Avoid duplicate benchmark workspaces.** The three checkouts account for roughly 1.9 GiB allocated in total. If a future benchmark needs independent workspaces from the same starting state, APFS file cloning can share unchanged extents and charge later writes separately. This helps checkout duplication, not the already-distinct VM guest writes, and ordinary `du` may double-count shared extents; measure filesystem free space. Apple documents [file cloning and shared blocks](https://developer.apple.com/documentation/foundation/about-apple-file-system) and [APFS sparse files](https://developer.apple.com/documentation/technologyoverviews/files-and-directories). Existing workspaces should remain intact until the saved VM/session-to-workspace mapping is no longer needed.

The [dev Dockerfile](../../platform/agent-execution/gondolin-session/gondolin/Dockerfile.dev)
now pins Playwright 1.58.2 and installs its Chromium revision 1208 into the
shared image. The bundled MCP browser revision 1237 remains present. A
[version check](../../platform/agent-execution/gondolin-session/gondolin/dev-image.test.mjs)
guards the pin against the client lockfile. A locally built image, using the
cached dev image as a stand-in for the builder-only Gitea base, was imported
into Gondolin. In a fresh VM, the client's `npx playwright install chromium`
changed `/ms-playwright` by just **4 KiB**, its checkpoint allocated **14.6 MiB**,
and Chromium launched successfully and loaded a page. The temporary local
test image and copied assets were removed afterward. Docker Desktop could
not resolve the builder-only `gitea.local` registry, so the source change was

from commit `b3b6cb6` on `codex/gitea-browser-image`. That workflow succeeded,
and the repository's local installer registered
`agent-workload-platform/dev:v1-v2-1965d60792308dc9fc87017c99914c92`
as Gondolin build `68878b87-6c91-5ab6-ac90-d915e17b6eaa`. A fresh VM from
this Gitea-built image ran Playwright 1.58.2, changed `/ms-playwright` by only
4 KiB when running `npx playwright install chromium`, launched Chromium and

archive and Docker image were removed after installation; the Gondolin image
remains installed. This change affects new images; saved VM checkpoints
continue to reference their original rootfs build.

## Constraints and validation

- **Do not run `qemu-img` against an active checkpoint or its active overlay.** The integration has a one-process lease at `<checkpoint>.lock`; offline compaction should use that lease, refuse when active, and maintain the current atomic-replacement behavior. QEMU's [image utility documentation](https://www.qemu.org/docs/master/tools/qemu-img.html) warns against modifying an image in use.
- **Do not assume guest `fstrim` saves host space today.** Gondolin 0.13.0 currently launches the root disk without `discard=unmap`; QEMU says discard requests reach the filesystem only with discard/unmap support. Guest deletion may leave old allocated clusters in a qcow2 even when the file is absent. Offline conversion is the immediate way to reclaim zero/unallocated sectors; enabling discard would require a separate Gondolin change and guest-to-host validation. Sources: [Gondolin QEMU launch](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/sandbox/controller.ts), [QEMU disk options](https://www.qemu.org/docs/master/system/qemu-manpage.html).
- **Preserve the backing rootfs build.** Gondolin validates the checkpoint's guest asset build ID on resume and may rebase the checkpoint in place if the recorded rootfs path moved. A portable archive therefore needs the matching rootfs assets and should be validated after a move. Sources: [Gondolin checkpoint resume](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/checkpoint.ts), [QEMU safe versus unsafe rebase](https://www.qemu.org/docs/master/tools/qemu-img.html).
- **Compare full guest-visible content, then boot it.** Ordinary `qemu-img compare` checks guest-visible sectors across image formats and backing chains, while `qemu-img check` detects qcow2 consistency problems. Do **not** use `compare -s` for this conversion: QEMU's strict mode also requires matching sector allocation, and the compressed copy had an expected block-status mismatch despite ordinary comparison passing. Neither check validates Gondolin's appended metadata or the Pi/session mapping; `VmCheckpoint.load` and a real resume/guest read complete the validation. Sources: [QEMU image utility](https://www.qemu.org/docs/master/tools/qemu-img.html), [Gondolin checkpoint loader](https://github.com/earendil-works/gondolin/blob/v0.13.0/host/src/checkpoint.ts).

## Recommended next experiment

Repeat the viable compression experiment on a **throwaway clone** across a resume, guest write, and subsequent checkpoint cycle, alongside ordinary sparse conversion and `zstd` compressed conversion. Keep the originals untouched. Record host allocated size, conversion time, ordinary `qemu-img compare` result, `VmCheckpoint.load` and resume result, and first guest command/resume latency. If savings justify the cost, add a lease-aware `compact` command that stages, validates, and replaces a checkpoint; retain explicit `dispose` as the only operation that intentionally deletes a task VM.
