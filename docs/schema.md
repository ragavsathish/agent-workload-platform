# Documentation knowledge schema

This file tells a maintainer or agent how to keep the [OKF bundle](index.md) coherent. The [format decision](adr/0003-adopt-okf-for-documentation.md) is binding; this schema describes the project workflow.

## Layers

1. **Source evidence:** product code and configuration, tests, [Allure measurements](evidence/allure/index.md), the [Löyly reference checkout](../loyly/README.md), and cited external sources. Preserve source identity and run/commit when available. Generated evidence is refreshed by its producer.
2. **Compiled wiki:** [wiki pages](wiki/index.md) synthesize stable concepts and link to source evidence. Update an existing page when new evidence changes its meaning; record contradictions and unresolved claims rather than creating a second competing summary.
3. **Contracts and journeys:** [context Gherkin](spec/contexts/index.md) owns local rules; [slice specs](plan/index.md) compose them across boundaries. [Event models](event-model/index.md) explore order and decision ownership. [ADRs](adr/index.md) record accepted choices. These are reviewed artifacts, not generated from an Allure pass.

## Operations

- **Ingest:** read the new source, identify affected concepts, compare it with the existing page and current/proposed status, update the relevant wiki pages and cross-links, then update the indexes and [log](log.md). Preserve source links and any conflict that remains unresolved.
- **Query:** start at [index.md](index.md), follow the smallest relevant area index, and distinguish a contract, a design proposal, and an observed measurement in the answer. Cite the precise document or run that supports the claim.
- **Lint:** check OKF frontmatter, local links, orphan pages, stale or contradictory claims, missing provenance, and whether generated evidence was edited by hand. Use `make docs-check` for structural checks; human review still decides semantic disagreements.

## File conventions

- All non-reserved `.md` files under `docs/` begin with YAML frontmatter containing `type`. Prefer `title`, a one-line `description`, and `sources` entries for claims derived from other material. Local `sources[].resource` paths resolve from the containing file. The working type vocabulary is `concept`, `reference`, `decision`, `plan`, `howto`, and `measurement`; OKF consumers must still accept unknown types.
- Use OKF v0.2 `status` only for document lifecycle: `draft`, `stable`, or `deprecated`. It does not say whether described product behavior is implemented, proposed, or verified. Put that claim state in the body, the plan status table, or a separate project-specific field. Omitted `status` means `stable`; do not infer human review from it. Add `generated` or `verified` only when the actor and timestamp can be established, and never imply a human review from an agent edit.
- `index.md` is a content catalog for its directory and has no frontmatter. `log.md` is chronological; append dated entries rather than rewriting history.
- Use ordinary relative Markdown links. Keep `.feature`, `.dsl`, `.svg`, `.png`, JSON, and code beside the topic that owns them; catalog them in Markdown instead of wrapping them in artificial Markdown copies.
- Preserve stable scenario IDs and exact result IDs. An extracted Allure file is regenerated by `docs/spec/extract_allure.py`; edits to observed steps belong in source tests or in a new reviewed contract.
