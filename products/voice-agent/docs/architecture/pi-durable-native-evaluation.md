# Pi Durable: native capability and migration boundary

> Historical evaluation of the pre-cutover worker. The current task path runs
> both host and Gondolin conversations through Pi Durable and is documented in
> [Pi Durable task-owner cutover](absurd-to-pi-durable.md).

Reviewed 2026-10-25 against the upstream [Pi Durable README](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md), [normative specification](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md), and [package manifest](https://github.com/earendil-works/pi/blob/main/packages/durable/package.json). Upstream calls the API **experimental** and says it can change without notice; the host runtime pins `@earendil-works/pi-durable` 1.4.0. This document records the original evaluation and the host migration completed afterward.

## Implemented host path

With `WORKER_PI_EXECUTION_MODE=host`, each agent invocation launches [pi-durable-task](../../../../platform/agent-execution/pi-durable-task/runtime.ts) instead of the Pi CLI/Rust supervisor. The runner opens a private SQLite store per task, uses the existing Pi `ModelRuntime` credentials, installs native `CodingTools` with `NodeExecutionEnv`, and submits the public task ID as the native `requestId`. The long-lived Pi Durable owner admits tasks directly from the voice session; the Gateway enforces caller identity and preserves the public task/result shape. Host agent-run and song-lyrics tasks reacquire the same native submission after restart. A small socket adapter maps the voice client's existing attachment protocol onto native `submit()` and `wait()`; it does not implement its own model or tool state machine.

The deployed browser journey completed a scratch task and downloaded its verified ZIP. A local real-model task reopened from SQLite with the same request ID, and the existing voice attachment client sent a follow-up to that conversation. The Gondolin mode remains on Pi CLI until its VM implements the `ExecutionEnv` contract. Native Durable forks, compaction, task graph, and other operations exist in the Harness but are not yet exposed through the product UI. The current host runner includes the installed skills directory in its agent instructions; it does not yet reproduce Pi CLI's extension and MCP discovery. Those are explicit parity gaps, not claimed features.

## Baseline before host migration

The [task worker](../../apps/worker/src/voice_worker/main.py) previously used Absurd/PostgreSQL to claim an `agent-run`, materialized a workspace, checkpointed a `run-intent`, launched the `pi` coding-agent CLI in RPC mode through the Rust `pi-task-rpc` supervisor, projected bounded progress, and captured a result artifact. The supervisor handled Pi JSONL RPC, attachment, and process lifetime. A crash after `run-intent` but before result checkpoint produced `needs_manual_reconciliation`. The Gateway now forwards direct task submissions to the Pi Durable owner and enforces the caller boundary. Both current execution modes use Pi Durable sessions directly.

## Native capability comparison

| Concern | Pi Durable 1.4.0 | Pre-migration path and implication |
| --- | --- | --- |
| Persistent conversation and restart | `Harness.open()` with SQLite or JSONL, then `root()` and `resume()`, restores stored conversation/task state. Submission `requestId` deduplicates retry; `harness.submission(id)` reacquires it. [README: Persist and Resume](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#persist-and-resume) | Absurd persists outer task/checkpoints; Pi CLI session JSONL persists transcript. The worker deliberately stops at manual reconciliation after an uncertain Pi run. Durable could own the agent run and remove that coarse uncertainty, subject to tool replay rules. |
| Tool crash semantics | Each tool call has persisted intent. Only a tool declared `replay: "safe"` runs again after mid-call death; otherwise the model receives an `interrupted` result. [README: Tools](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#tools) | Current worker treats the whole Pi invocation as an opaque side effect. Native semantics are finer grained, but they do **not** make arbitrary host commands exactly once or automatically safe to retry. |
| Active conversation | Native busy-conversation inbox supports queued follow-ups, `whenBusy: "steer"`, `whenBusy: "reject"`, write-only entries, and withdrawal. [README: Busy Conversations](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#busy-conversations) | Current RPC supervisor accepts bounded attach/command operations around a CLI session. Durable can become the source of truth for follow-up and steering behavior instead of duplicating it in RPC or the worker. |
| Fork, context, and background work | `fork(entryId)` creates an independent conversation; reset/handoff, compaction, task-owned child conversations, background tasks, abort, and a live task graph are native. [README: More Conversations and Forks](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#more-conversations-and-forks), [Abort and Subagents](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#abort-and-subagents), [Task Graph](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#task-graph) | The current `agent-run` is one bounded invocation. Exposing these native features would expand the user journey rather than emulate them in Absurd task parameters. |
| Live UI and telemetry | `watch()` exposes committed view plus changes; experimental `watchEvents()` emits agent-style message/tool events from those commits. Native usage and telemetry schemas expose task/phase counts without requiring raw text. [README: Watching a Conversation](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#watching-a-conversation), [Agent Events](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#agent-events-experimental), [Usage and Cost](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#usage-and-cost) | We currently parse Pi event lines and store selected spoken progress. A gateway projection could consume Durable's view/events while preserving today's bounded public response. `watchEvents()` is explicitly experimental. |
| Tools and execution location | `CodingTools` supplies `read`, `write`, `edit`, and `bash`. Every call uses a host supplied `ExecutionEnv`; `NodeExecutionEnv` runs on the local host. A custom environment can represent a per-conversation container or VM. [README: Tools](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#tools), [Environment](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#environment) | The deployment mode selects **the environment for all durable task sessions**: local Mac host tools for `host`, task VM tools for `gondolin`. Submission and caller identity remain the same across modes. A Gondolin `ExecutionEnv` adapter needs implementation and conformance testing. |
| Storage and ownership | Node SQLite is a local file with WAL `synchronous=NORMAL`; JSONL can fsync commit markers but holds history in memory. Only one process may own a store; there is no cross-process locking. The spec's task/conversation *owner* is for attribution and abort traversal, **not an access-control capability**. [README: Storage](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#storage), [spec: core records](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md#2-core-records) | The Mac uses one long-lived Pi Durable owner with SQLite. The Gateway connects through its bounded private API and retains separate product authorization. |

## Boundary recommendation

Use `WORKER_PI_EXECUTION_MODE=host|gondolin` as **one deployment-wide choice for the durable Pi execution environment**. Keep task submission and tailnet owner checks independent of that flag. Pi Durable's `HarnessOptions.identity` identifies the app to **model providers**; it is not the Gateway's user authentication or task-ownership mechanism. The upstream Pi repository also states that Pi does not include a built-in filesystem/process/network/credential permission system and runs with the launching account's permissions by default. [README: Harness identity](https://github.com/earendil-works/pi/blob/main/packages/durable/README.md#quick-start), [Pi repository: Permissions & Containerization](https://github.com/earendil-works/pi#permissions--containerization), [spec: ownership](https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md#2-core-records)

For the remaining Gondolin migration, implement a task-scoped `ExecutionEnv` over the Gondolin VM and run Pi Durable's environment conformance suite before switching that deployment mode. Keep the public task ID mapped to one native submission and keep the Gateway and artifact contract unchanged. Do not add a second model/tool state machine to the Rust supervisor or Python worker. An integration test should interrupt a live tool call, reopen its SQLite store, and verify Pi Durable's safe versus unsafe replay behavior against the task artifact. The [product task-owner cutover](absurd-to-pi-durable.md) is complete. Finally, expose native forks, compaction, task graph, and usage through bounded owner queries only when their user journeys are defined. Extension and MCP parity with Pi CLI should be tested before retiring the CLI path.
