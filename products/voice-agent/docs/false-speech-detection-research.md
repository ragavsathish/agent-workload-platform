# False speech detection and barge-in research

Date: 2026-10-23. Scope: this repository's Pipecat 1.12.0 voice edge, Silero VAD, SmallWebRTC browser client, segmented REST STT, and Smart Turn. This note distinguishes observed behavior from possible causes; it proposes measurements before changing detection thresholds.

## What is established

The current edge configures `SileroVADAnalyzer(VADParams(stop_secs=0.2))` in `apps/edge/bot.py`. The unspecified Pipecat 1.12.0 defaults are `confidence=0.7`, `start_secs=0.2`, and `min_volume=0.6`. Pipecat calls a VAD start speech only after both probability and volume pass their thresholds for the start duration. It then marks a user turn; by default, the start strategy also broadcasts an interruption. This happens before any STT text. Smart Turn evaluates *turn end*, so changing Smart Turn cannot prevent an initial false barge-in. Sources: [Pipecat 1.12.0 VAD analyzer](https://github.com/pipecat-ai/pipecat/blob/v1.12.0/src/pipecat/audio/vad/vad_analyzer.py), [VAD start strategy](https://github.com/pipecat-ai/pipecat/blob/v1.12.0/src/pipecat/turns/user_start/vad_user_turn_start_strategy.py), [turn strategy lifecycle](https://docs.pipecat.ai/api-reference/server/utilities/turn-management/user-turn-strategies#how-it-works).

The previous incident investigation correlated three speech-start/interruption events with empty user turns and no corresponding transcript. The already deployed `empty_user_turn=None` prevents Pipecat's synthetic “please repeat” response for those turns, but does not prevent VAD from interrupting bot audio. The diagnostic recording showed low filtered audio levels near two events and a louder level near one. Those 1-second audio levels are neither event-aligned model probabilities nor proof that a real sound did not occur. A prior offline Silero replay failed to reproduce two events. **The physical cause and the exact stage that misclassified the input remain unproven.** This paragraph records the prior local incident investigation; the first-party sources above establish the software mechanism, not the incident cause.

The client creates `SmallWebRTCTransport()` with `enableMic: true` but specifies no microphone-processing constraints. The bundled `@pipecat-ai/small-webrtc-transport` 1.10.8 implementation calls `getUserMedia({audio: true})`, or `{audio: {deviceId}}` when a device is selected. Browser and device defaults can differ. The [W3C Media Capture specification](https://www.w3.org/TR/mediacapture-streams/#constrainable-properties) says user agents choose defaults for properties such as echo cancellation; [MDN's track settings documentation](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings) shows how to inspect the applied `echoCancellation`, `noiseSuppression`, and `autoGainControl` values. The client is hosted in macOS WKWebView, so its actual track settings should be read in that runtime rather than inferred from Chrome or Firefox.

The server applies the selected `voxlock` audio filter before the aggregator's VAD. Thus diagnostics must compare the browser capture, raw received samples, and **filtered samples reaching VAD**. The deployed selection is `VOICE_INPUT_FILTER=voxlock`; `apps/edge/audio_filter.py` records bounded raw and filtered WAV diagnostics and dBFS summaries. This establishes where to measure, not that VoxLock caused the events.

## Use the existing diagnostics page

The app already opens `/diagnostics/` from **Input diagnostics**. For each of the last five completed conversations it shows raw and filtered audio replays, waveforms, spectrograms, input/output dBFS, suppression, filter latency, and VoxLock model-state charts. Its live view polls the current microphone envelope. These are backed by `/api/audio-diagnostics` and the private diagnostic volume; the sixth completed conversation removes the oldest. Sources: `apps/diagnostics/src/AudioDiagnosticsView.tsx`, `apps/diagnostics/src/AudioDiagnosticsCharts.tsx`, `apps/diagnostics/src/AudioWaveform.tsx`, `apps/edge/audio_filter.py`, and `apps/edge/audio_diagnostics.py`.

That page is the right place to investigate and replay this incident. The follow-up instrumentation now adds the browser microphone track's applied settings, Pipecat's VAD confidence and smoothed volume, and VAD/interruption/transcript markers on the audio timeline. Bot-speaking event markers provide a playback comparison, though they use the recorder's input clock and may differ slightly from the filtered VAD clock. The page still cannot prove that speaker playback leaked into the microphone merely from a coincident marker; compare the raw replay and a headphones run.

## Fix candidates and tradeoffs

| Candidate | Expected effect | Limitation / decision |
|---|---|---|
| Verify browser capture and audio routing | `track.getSettings()` exposes applied echo cancellation, noise suppression and gain control; a headphones-versus-speakers comparison can reveal playback leakage. | A setting value alone does not prove that echo cancellation works for this device. If leakage is observed, request explicit supported constraints and repeat the same test. [W3C](https://www.w3.org/TR/mediacapture-streams/#constrainable-properties), [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capture_and_Streams_API/Constraints). |
| Tune Pipecat's VAD *start* evidence | Raising `confidence`, `start_secs`, or `min_volume` can reject weaker or shorter candidate speech. Pipecat 1.12.0 applies all three before starting. | May miss quiet speech, short words, or slow starts. Choose values from event-aligned probabilities and a labeled local replay set; do not tune `stop_secs` for false *starts*. [Pipecat source](https://github.com/pipecat-ai/pipecat/blob/v1.12.0/src/pipecat/audio/vad/vad_analyzer.py), [Silero tuning FAQ](https://github.com/snakers4/silero-vad/wiki/FAQ#how-to-tune-the-hyper-parameters). |
| Make interruption depend on transcript | Pipecat's `MinWordsUserTurnStartStrategy` requires words before starting, and can distinguish bot-speaking from idle states. | This application uses segmented REST STT, not interim streaming transcriptions, so text arrives only after a segment ends. It would delay or suppress real-time barge-in. Treat as an architectural change, not a safe one-line fix. [Pipecat docs](https://docs.pipecat.ai/api-reference/server/utilities/turn-management/user-turn-strategies#minwordsuserturnstartstrategy), [Pipecat 1.12.0 source](https://github.com/pipecat-ai/pipecat/blob/v1.12.0/src/pipecat/turns/user_start/min_words_user_turn_start_strategy.py). |
| Disable interruption on VAD start | `enable_interruptions=False` stops this strategy from broadcasting an interruption. | Genuine user barge-in would also stop working through that path; it only suits an intentional no-barge-in mode or a replacement start strategy. [Pipecat docs](https://docs.pipecat.ai/api-reference/server/utilities/turn-management/user-turn-strategies#base-parameters). |
| Use a separate interruption classifier | Pipecat offers Krisp VIVA IP to distinguish an intentional interruption from backchannels, with transcription as a fallback. | Adds a separate model, SDK, and key; it is not evidence that this incident came from a backchannel or that the model will handle silent artifacts. Evaluate only after identifying the unwanted input. [Pipecat docs](https://docs.pipecat.ai/api-reference/server/utilities/turn-management/user-turn-strategies#krispvivaipuserturnstartstrategy). |

The standalone Silero package documents threshold and minimum speech duration tuning on its own timestamping API. Those options do **not** map one-to-one to Pipecat's streaming `VADParams`; Pipecat's `start_secs` and probability/volume gates are the relevant controls here. See [Silero's FAQ](https://github.com/snakers4/silero-vad/wiki/FAQ#how-to-tune-the-hyper-parameters) and [Pipecat's VAD analyzer](https://github.com/pipecat-ai/pipecat/blob/v1.12.0/src/pipecat/audio/vad/vad_analyzer.py).

## Recommended validation before a config change

1. Open the existing `/diagnostics/` page for the affected conversation. Compare its raw and VoxLock replays and charts at the approximate interruption times. The page currently retains only five completed conversations, so preserve the affected session before it is pruned if further testing is needed.
2. Check the applied microphone track settings shown on the page, then compare speakers and headphones with the same microphone and speech script. Device identifiers are deliberately excluded from telemetry and the view. If the issue occurs only during bot playback, test echo leakage; if it occurs while the bot is quiet, focus on ambient sound and the filter/VAD boundary.
3. Select a false-start marker on the existing replay timeline and inspect its six-second window. Compare Pipecat VAD confidence and smoothed volume with the thresholds, bot-speaking markers, and whether STT later emitted text. Older recordings made before this instrumentation have only dBFS charts and no VAD event markers.
4. Replay the *exact filtered input delivered to VAD*, with the same Pipecat version, sample rate, chunk boundaries, filter state, and start parameters. Label quiet room, bot playback, ambient noise, deliberate short barge-in, soft speech, and ordinary speech. Measure false interruptions alongside missed legitimate interruptions and detection latency.
5. Only then test a small change to one start parameter at a time. Preserve `stop_secs=0.2` unless a separate turn-end problem is demonstrated. Use live WKWebView tests as the final gate because browser processing and playback routing may not reproduce offline.

The capture-to-VAD decision is now instrumented on the existing diagnostic page. A controlled browser/endpoint test and event review are still needed before choosing a detection setting. The existing empty-turn fix addresses what the agent says after a false start; it does not establish a fix for the false start itself.
